# PRD — 마커 주행(ArUco Marker Drive) 1단계

설계문서: `docs/design-marker-drive.md`
작성일: 2026-07-27 · 레포: `arte_aurcomaker_move` (단독 실행)

## Problem Statement

로봇이 지정된 지점에 정밀하게 붙어야 하는데, 지금 쓸 수 있는 수단이 없다.

- nav2/AMCL 은 목표 **근처**까지만 데려다준다. 마지막 수십 cm 에서 추정 오차가 물리적
  여유보다 커진다.
- 기존 저장소(`aba_project`)에 ArUco 정밀 도킹 코드가 있지만 **로봇에서 실행할 통로가 없다.**
  그 코드는 로봇 온보드 웹서버에 마운트돼 있는데 실제 로봇 부팅 구성이 그 웹서버를 띄우지
  않는다. 띄우면 카메라 장치를 직접 열어 영상 송출 프로세스와 충돌한다.
- 그래서 마커 주행 로직을 실기에서 **튜닝해 본 적이 없다.** 조향 극성, yaw 신뢰 거리 같은
  값은 현장에서 돌려 봐야만 정해지는데 돌릴 방법이 없었다.

## Solution

**마커 한 장을 보고 그 앞 10cm 에 서는 주행 코어**를, 다른 스택에 얹히지 않는 **단독 레포**로
만든다. 로봇에서 이 레포만 돌리면 카메라도 속도 명령 토픽도 경합이 없다.

사용자 관점에서 달라지는 것:

- 로봇 앞에서 명령 한 줄로 마커 주행을 돌려보고, 안 맞으면 **CLI 플래그만 바꿔 즉시 재실행**한다.
- 마커가 시야에 없어도 로봇이 좌우를 훑어 찾는다.
- 어떤 ArUco 사전을 쓴 마커인지 몰라도 **검출 모드가 알려 준다.**
- 노트북에서 같은 순간의 검출 상태를 눈으로 본다.
- 실패는 조용하지 않다. 못 찾으면 멈추고 이유를 말한다.

튜닝이 끝난 이 코어는 나중에 `aba_project` 의 미션 BT 에 그대로 얹는다. 그때 바뀌는 것은
프레임을 어디서 받아오는가 **한 함수뿐**이다.

## User Stories

1. 로봇 운영자로서, 마커 앞 10cm 에 로봇이 자동으로 서기를 원한다. 손으로 밀어 맞추지
   않아도 되기 때문이다.
2. 로봇 운영자로서, 정지 거리가 로봇 **최전방** 기준이기를 원한다. 카메라 기준이면 몸체가
   이미 벽에 닿아 있을 수 있기 때문이다.
3. 로봇 운영자로서, 마커가 안 보이는 자리에서 시작해도 로봇이 스스로 찾기를 원한다. 시작
   위치를 사람이 정밀하게 맞춰 줄 수 없기 때문이다.
4. 로봇 운영자로서, 탐색이 좌우 ±60° 를 20° 씩 끊어 돌며 멈춰서 보기를 원한다. 연속으로
   돌면 모션블러로 마커를 놓치기 때문이다.
5. 로봇 운영자로서, 한 바퀴 훑고도 못 찾으면 제자리에서 멈추기를 원한다. 무한정 도는 로봇은
   배터리를 태우고 사람을 불안하게 만들기 때문이다.
6. 로봇 운영자로서, 주행 중 Ctrl-C 로 즉시 멈출 수 있기를 원한다. 모터를 물고 있는
   프로그램에서 그것이 유일한 비상구이기 때문이다.
7. 로봇 운영자로서, 로봇이 마커에 비스듬히 도착하지 않기를 원한다. 도킹 면이 어긋나면 정지
   거리가 맞아도 실패이기 때문이다.
8. 로봇 운영자로서, 벽에 박기 전에 스스로 멈추기를 원한다. 시각 정보가 끊기는 마지막
   구간에서도 안전해야 하기 때문이다.
9. 로봇 운영자로서, 별도 서버나 관제 없이 로봇 한 대만으로 실행되기를 원한다. 튜닝하려고
   스택 전체를 띄우는 것은 과하기 때문이다.
10. 튜닝 담당자로서, 조향 극성을 코드 수정 없이 플래그로 뒤집기를 원한다. 그 값은 현장에서
    돌려 봐야만 정해지기 때문이다.
11. 튜닝 담당자로서, yaw 를 신뢰하기 시작하는 거리를 플래그로 바꾸기를 원한다. 단일 평면
    마커의 자세 추정은 먼 거리에서 해가 뒤집히기 때문이다.
12. 튜닝 담당자로서, 정지 거리와 카메라-최전방 오프셋을 플래그로 주기를 원한다. 로봇 기구가
    바뀌면 그 값도 바뀌기 때문이다.
13. 튜닝 담당자로서, 모터를 돌리지 않고 검출만 확인하는 모드를 원한다. 마커 부착 위치와
    조명을 먼저 잡아야 주행 튜닝이 의미를 갖기 때문이다.
14. 튜닝 담당자로서, 검출 모드가 마커까지 거리와 함께 **로봇 앞면까지 남은 거리**를 출력하기를
    원한다. 오프셋을 자로 재지 않고 화면에서 확인하기 위해서다.
15. 튜닝 담당자로서, 벽에 붙은 마커가 어떤 사전으로 만들어졌는지 프로그램이 알려 주기를
    원한다. 사전이 틀리면 오류가 아니라 검출 0개로 조용히 실패하기 때문이다.
16. 튜닝 담당자로서, 튜닝 한 번에 빌드 단계가 끼지 않기를 원한다. 고치고 다시 돌리는 주기가
    튜닝 속도를 지배하기 때문이다.
17. 튜닝 담당자로서, 노트북에서 로봇 카메라의 검출 결과를 실시간으로 보기를 원한다. 로봇
    화면을 들여다보며 주행시킬 수는 없기 때문이다.
18. 튜닝 담당자로서, 노트북 관찰 도구가 모터를 절대 건드리지 않기를 원한다. 관찰이 주행에
    영향을 주면 관찰이 아니기 때문이다.
19. 튜닝 담당자로서, 마커가 몇 m 부터 안정적으로 잡히는지 확인하기를 원한다. 그 값이 탐색
    범위와 접근 시작 거리를 정하기 때문이다.
20. 개발자로서, 제어 상태기계가 카메라·모터·시계를 모르는 순수 함수이기를 원한다. 로봇 없이
    전체 판단 로직을 테스트할 수 있어야 하기 때문이다.
21. 개발자로서, 프레임을 어디서 받는지가 **함수 하나**에 갇혀 있기를 원한다. 나중에 다른
    스택 위로 올라가면 그 함수만 바뀌어야 하기 때문이다.
22. 개발자로서, 상태기계 어디에도 카메라 읽기 호출이 등장하지 않기를 원한다. 흩어져 있으면
    승격 때 전부 찾아 고쳐야 하기 때문이다.
23. 개발자로서, 같은 코어를 나중에 뒷 카메라 후진 정렬에도 쓰기를 원한다. 방향과 카메라만
    다르고 판단 구조는 같기 때문이다.
24. 개발자로서, 검출·자세추정 방식이 기존 도킹 구현과 동일하기를 원한다. 그 방식은 작은
    마커에서 정면각 부호가 튀는 문제를 이미 겪고 고른 것이기 때문이다.
25. 개발자로서, 제어 게인과 펄스 길이가 현장에서 검증된 기존 값이기를 원한다. 새로 지어내면
    튜닝을 처음부터 다시 하게 되기 때문이다.
26. 개발자로서, 검출 코드가 OpenCV 4.6 과 4.7+ 양쪽에서 돌기를 원한다. 로봇과 노트북의
    설치 버전이 다르기 때문이다.
27. 개발자로서, 카메라 종류(CSI/USB)에 따라 프레임 획득 방식이 갈리는 것을 한 곳에서만
    처리하기를 원한다. CSI 는 일반 캡처 API 로 검은 화면만 나오기 때문이다.
28. 개발자로서, 어느 카메라인지가 곧 캘리브레이션 선택 키이기를 원한다. 회전 보정이 다른
    캘리브를 물리면 거리는 그럴듯한데 정렬만 한쪽으로 흐르기 때문이다.
29. 개발자로서, 캘리브레이션 파일이 이 레포 안에 있기를 원한다. 다른 저장소 경로에 의존하면
    로봇에 이 레포만 내려받았을 때 못 돈다.
30. 개발자로서, 카메라가 죽은 상황과 마커가 안 보이는 상황이 구분되기를 원한다. 카메라가
    멈췄는데 탐색만 계속 도는 것이 최악의 실패 형태이기 때문이다.
31. 개발자로서, 탐색 회전량이 시간 추정이 아니라 주행거리계 피드백으로 닫히기를 원한다.
    바닥 재질과 배터리 잔량에 따라 같은 시간의 회전량이 달라지기 때문이다.
32. 개발자로서, 시각 정보 없는 마지막 구간의 전진도 주행거리계로 재기를 원한다. 몇 cm
    구간이라도 추측으로 밀면 정지 위치가 매번 달라지기 때문이다.
33. 개발자로서, 모터 명령이 관리자 권한을 요구하지 않기를 원한다. 권한을 물으면 자동화에서
    그대로 막히기 때문이다.
34. 개발자로서, 마커 상실이 마지막 관측 거리에 따라 다르게 처리되기를 원한다. 멀리서 놓친
    것과 가까워져 시야에서 빠진 것은 정반대 상황이기 때문이다.
35. 개발자로서, 정렬이 수렴하지 않으면 제한 시간 뒤 포기하기를 원한다. 제자리에서 영원히
    미세 조정하는 로봇은 실패를 숨기기 때문이다.
36. 개발자로서, 전진 중 진전이 없으면 막힘으로 판정하기를 원한다. 바퀴가 헛돌거나 장애물에
    걸린 상태를 계속 밀어붙이면 안 되기 때문이다.
37. 개발자로서, 근접 안전 감시가 필터되지 않은 원본 거리 데이터를 쓰기를 원한다. 필터된
    쪽은 근접 구간이 제거돼 있기 때문이다.
38. 시험 담당자로서, 실행 전에 무엇이 떠 있어야 하고 무엇이 꺼져 있어야 하는지 스크립트가
    확인해 주기를 원한다. 매번 같은 함정에 빠지지 않기 위해서다.
39. 유지보수자로서, 상태기계 테스트가 로봇 없이 돌기를 원한다. 회귀를 잡는 데 하드웨어
    예약이 필요하면 아무도 안 돌리기 때문이다.
40. 유지보수자로서, 이 레포가 다른 저장소의 코드를 임포트하지 않기를 원한다. 단독으로
    내려받아 돌 수 있어야 하기 때문이다.

## Implementation Decisions

### 실행 형태

- **단독 실행.** 다른 스택(추종·영상송출·nav2)을 띄우지 않는다. 필요한 외부 요소는 로봇
  구동 노드(속도 명령 구독, 주행거리계·레이저 발행)뿐이다.
- 카메라는 이 프로그램이 **직접 연다.** 다른 프로세스와 경합하지 않으므로 가능하다.
- 프레임 획득은 **함수 하나**로 감싼다. 나중에 다른 스택 위로 올라가면 그 함수만 공유메모리
  읽기로 바꾸고 상태기계는 손대지 않는다.
- 로봇에서 빌드 단계 없이 실행한다(순수 파이썬).

### 마커

- 5x5 계열, 한 변 0.07 m, ID 1. 기본 사전은 `DICT_5X5_100`.
- 5x5 계열은 하위 사전마다 비트 패턴이 달라 틀리면 검출이 0개가 된다. 검출 모드에 **사전
  자동 스캔**을 넣어 실물이 어떤 사전인지 프로그램이 답하게 한다.

### 정지 조건

- 목표는 **마커에서 로봇 최전방까지 0.10 m**. 판정식은 `마커거리 ≤ 목표 + 카메라-최전방 오프셋`,
  오프셋 기본 0.
- 7cm 마커는 약 12.6cm 부터 검출이 불안정해진다. 남는 2~3cm 는 주행거리계로 전진한다.
- 근접 안전 감시는 **필터 전 원본 레이저 스캔**의 전방 섹터를 쓴다.

### 제어

- 속도 명령 토픽 발행만 사용한다. 관리자 권한이 필요한 하드웨어 직접 제어를 쓰지 않는다.
- 원거리 접근만 비례 조향 + 연속 전진. 탐색·근거리 정렬·마지막 전진은 펄스 방식이다.
- 탐색은 좌우 ±60° 를 20° 씩 끊어 돌고, 회전량은 주행거리계 방위각으로 닫는다.
- 게인·데드밴드·펄스 길이는 기존 구현의 현장 검증값을 전사한다. 조향 극성도 그 값을
  기본값으로 두되 플래그로 뒤집을 수 있다.
- 게이트 밖에서는 마커 정면각을 쓰지 않고 화면 중앙 오차만 쓴다.

### 상태기계

- 단계: 탐색 → 원거리 접근 → 근거리 축 정렬 → 무시각 전진 → 완료/중단.
- 마커 상실은 마지막 관측 거리로 갈린다. 멀면 탐색 복귀, 가까우면 무시각 전진.
- 중단 이유는 문자열로 남긴다: 미발견 / 시간초과 / 근접감지 / 막힘 / 정렬미수렴.
- 판단 로직은 순수 함수다. 입력은 관측값·전방거리·방위각·누적거리·경과시간, 출력은
  선속도·각속도·단계·완료여부·이유.

### 캘리브레이션

- 이 레포 안 `config/camera/` 에 둔다(기존 저장소에서 복사). 다른 저장소 경로를 참조하지 않는다.
- 슬롯 이름(front/back)이 곧 파일 선택 키다. 앞은 180° 회전 보정본, 뒤는 USB 용.

### 호환성

- `cv2.aruco` API 는 4.6 과 4.7+ 가 다르다. 두 경로를 모두 지원한다.
- CSI 카메라는 일반 캡처 API 로 검은 화면만 나오므로 전용 경로를 쓰고, USB 는 일반 경로를
  쓴다. 이 분기는 프레임 획득 함수 안에서만 처리한다.

## Testing Decisions

**좋은 테스트의 기준**: 외부에서 관찰 가능한 동작만 검증한다. 내부 변수명·호출 순서·중간
계산값은 보지 않는다. 순수 함수에 입력 시퀀스를 넣고 나오는 명령과 단계 전이를 확인한다.
하드웨어·ROS·네트워크를 요구하는 테스트는 만들지 않는다.

**테스트 대상**
- 제어 상태기계 — 전 단계 전이와 중단 조건
- 검출 — 합성 마커 이미지를 만들어 거리·좌우오차 부호·ID 필터 검증(카메라 불필요)
- 설정 — 현장 검증 상수 기본값이 유지되는지, 범위 강제가 도는지

ROS 어댑터(주행거리계·레이저)와 카메라 획득은 자동 테스트하지 않는다. 실행 환경이 본질이라
단위 테스트가 실제 결함을 못 잡는다. 검출 모드 실행으로 확인한다.

**선례**: 기존 저장소의 추종 인지 패키지에 ROS 없는 순수 로직 테스트가 여럿 있다(제어 루프·
PID·탐색 계획·회피). 같은 형태를 따르되, 이 레포는 독립이므로 코드를 임포트하지 않는다.

## Out of Scope

- 미션 BT 배선(주차 방향 정렬 / 도킹 정렬) — 3단계, 다른 저장소
- 뒷 카메라 후진 정렬 — 3단계
- 다른 저장소 코드 수정(영상 송출 프로세스의 생프레임 탭, 추종 명령 브릿지 등) — 단독 실행에서는 불필요
- 관제 화면·API 연동
- 마커 여러 장을 잇는 경로 주행, ChArUco, 중첩 마커
- 속도 명령 중재자 도입
- 마커를 이용한 지도 상 위치 보정

## Further Notes

- **왜 기존 도킹 코드를 임포트하지 않는가**: 그 코드는 다른 저장소의 웹서버 라우터에 묶여
  있어 임포트하면 웹 프레임워크 의존이 딸려온다. 이 레포는 단독으로 돌아야 한다. 구조는 새로
  짜되 검출 방식과 현장 검증 상수는 전사한다.
- **조향 극성은 소프트웨어로 결정할 수 없다.** 기존 구현의 해당 상수에는 현장 재검증 기록이
  주석으로 남아 있다. 이번에도 실기에서 확정한다.
- **거리 정확도 기대치**: 마커 거리 추정 오차 약 3%, 검출 한계에서 4mm. 무시각 구간의
  주행거리계 오차를 더해도 목표 대비 ±5mm 수준.
- **실행 전 체크리스트**: 로봇 구동 노드가 떠 있을 것, 다른 스택이 카메라·속도 명령 토픽을
  잡고 있지 않을 것, 마커가 카메라 높이에서 정면으로 보일 것.
- 실패 시 로봇은 그 자리에 멈추고 이유를 남긴다. 재시도·우회 동작은 이번 범위가 아니다.
